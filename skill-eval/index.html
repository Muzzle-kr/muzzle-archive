Method / 어떻게 읽었나

무작정 “좋아 보이는 방법”을 모은 게 아니라, 최근 자료에서 반복적으로 재등장한 패턴만 세었습니다.

중요: 이 순위는 “정답 순위”가 아니라 최근 22개 공개 소스에서 얼마나 자주 명시적으로 쓰였는지를 기준으로 한 빈도 순위입니다. 같은 스킬이 마켓플레이스와 GitHub에서 동시에 반복 노출된 경우도 포함했습니다. 이유는, 그 중복 자체가 “사람들이 이 방식을 패키징하고 재사용한다”는 신호이기 때문입니다.

What Counted

스모크 테스트, 루브릭, 대표 시나리오, 회귀 비교, 툴 트레이스 확인처럼 실제 행동 평가 방법만 메인 랭킹에 넣었습니다.

What Did Not

GitHub stars, 다운로드 수, “Best Skills” 글의 추천 순위는 탐색 필터로는 봤지만, 본문 랭킹 점수에는 직접 넣지 않았습니다.

Date Handling

GitHub는 commit/modified 날짜를, 공식 글은 게시일을, 마켓플레이스는 페이지가 노출한 update/crawl 메타데이터를 기록했습니다.

Top Patterns / 방식별 해설

각 패턴마다 “실제로 어떻게 생겼는지”, “왜 자주 쓰이는지”, “어디서 확인됐는지”만 짧고 선명하게 정리했습니다.

#1 Smoke Tests / 스모크 테스트

가장 흔한 방식은 긴 품질 평가가 아니라 핵심 기능이 살아 있는지 빠르게 확인하는 통과/실패 게이트였습니다. 특히 배포 직후, 설정 변경 직후, 큰 리팩터 뒤에 바로 붙습니다.

What It Looks Like

  • 3분~15분 안쪽
  • 인증, 헬스체크, 핵심 경로만 확인
  • 대개 단일 명령 또는 짧은 alias 제공
  • 결과는 pass/fail 또는 매우 짧은 요약

Why It Wins

사람들이 원하는 첫 질문은 “완벽한가?”가 아니라 “망가졌는가?”입니다. 비용이 가장 낮고, 자동화하기 쉽고, 실패했을 때 바로 멈출 수 있어서 모든 팀이 기본 레이어로 채택하기 좋습니다.

#2 Rubrics / 루브릭과 가중치 점수

두 번째로 많이 나온 건 평가 항목을 고정하고 점수를 매기는 방식입니다. 여기서 중요한 건 숫자보다도, “무엇을 보고 좋은지 판단하는가”를 미리 고정한다는 점입니다.

What It Looks Like

  • 4~8개 평가 기준
  • 1~5 scale 또는 tiered rating
  • 가중치와 최소 통과선 설정
  • 좋은 예/나쁜 예 descriptor 포함

Why It Wins

Skill 평가는 쉽게 “느낌” 싸움이 됩니다. 루브릭은 그 느낌을 반복 가능한 체크리스트로 바꿔서, 여러 사람이 봐도 비슷한 결론에 도달하게 도와줍니다.

#3 Representative Scenario Suites / 대표 시나리오 세트

Skill은 논문 문제를 푸는 게 아니라 실제 워크플로를 수행하는 도구라서, 추상적 벤치마크보다 “현실적인 요청 몇 개”가 훨씬 자주 쓰였습니다.

What It Looks Like

  • 5~15개 대표 요청 세트
  • 정상 케이스 + 엣지 케이스 + 거절 케이스
  • 실제 사용자 문장과 비슷한 프롬프트
  • 작업 완료까지 end-to-end 평가

Why It Wins

Skill은 “답변 품질”보다 흐름을 끝까지 잘 수행하느냐가 중요합니다. 그래서 대표 시나리오 세트는 가장 설명력이 높고, 현업 사람이 결과를 이해하기도 쉽습니다.

#4 Baseline + Regression Diff / 기준선과 회귀 비교

“새 버전이 더 똑똑한가?”보다 실제 현업은 “이전보다 나빠지지 않았는가?”를 먼저 봅니다. 그래서 baseline 저장과 regression 비교가 매우 자주 등장했습니다.

What It Looks Like

  • 기준 JSON 또는 과거 점수 저장
  • 변경 후 비교 diff 생성
  • 점수 하락 시 merge/block
  • PR smoke, nightly full suite 분리

Why It Wins

Skill 개발은 작은 수정이 큰 부작용을 만들기 쉽습니다. baseline은 “좋아졌는지”보다 “기존에 되던 걸 깨뜨렸는지”를 싸고 명확하게 보여줍니다.

#5 Deterministic Checks / 골든 파일, 스키마, 정확한 assertion

LLM judge만 믿지 않고, 먼저 정확하게 맞다/아니다를 판별할 수 있는 것들부터 따지는 패턴입니다.

What It Looks Like

  • golden output 비교
  • JSON/schema validation
  • regex/assertion checks
  • mock tools로 side effect 고정

Why It Wins

자동 평가는 쉽게 흔들립니다. 결정적 체크는 노이즈를 줄이고, 재실행했을 때 같은 결과를 얻도록 도와줍니다. 그래서 많은 팀이 “정답이 명확한 부분”은 꼭 분리합니다.

#6 Tool Trace Verification / 툴 사용 경로까지 검증

Skill은 결과 텍스트만 잘 쓰면 끝이 아닙니다. 올바른 툴을, 올바른 순서로, 불필요한 위험 없이 썼는가도 점점 중요한 평가 항목이 됐습니다.

What It Looks Like

  • 사용한 툴 목록 검사
  • 호출 순서와 side effect 확인
  • 스크린샷, diff, 로그 첨부
  • 재시도 횟수, early-exit 확인

Why It Wins

같은 결과라도 과정이 불안정하면 실전에서 터집니다. 특히 Codex류 도구는 file edit, command run, diff acceptance가 핵심이어서 행동 경로 자체를 보는 문화가 강합니다.

#7 Human Evidence Review / 사람이 끝까지 증거를 읽는 단계

자동 점수는 늘어나고 있지만, 여전히 많은 팀이 diff, screenshot, transcript를 사람이 직접 확인합니다. 특히 실패 원인 해석과 애매한 경계 사례에서는 이 단계가 빠지지 않았습니다.

Why It Stays

자동 점수는 빨라도, “이 실패가 실제로 중요한가?”는 사람이 가장 잘 판단합니다. 그래서 고성숙 팀일수록 자동화만 믿지 않고 증거 묶음을 함께 남깁니다.

#8 Multi-run Reliability / 여러 번 돌려서 보는 신뢰도

한 번 잘 되더라도, 실제로는 두 번째나 세 번째에 깨지는 Skill이 많습니다. 그래서 일부 소스는 variance, repeatability, pass@k를 별도로 기록했습니다.

Why It Matters

“된다”와 “늘 된다”는 다릅니다. 운영 환경으로 갈수록, 이 차이가 가장 비싸게 돌아옵니다.

#9 Adversarial / Hidden / Refusal Tests / 이상 케이스 일부러 찌르기

프롬프트 인젝션, 툴 장애, 거절해야 하는 요청, 숨은 평가 세트는 아직 메인스트림은 아니지만, 보안·안정성에 민감한 팀에서는 분명히 강화되고 있었습니다.

Why It Is Lower

중요성은 크지만 만들고 유지하기 어렵습니다. 그래서 “모두가 하는 기본 평가”보다는 한 단계 높은 성숙도의 신호로 보였습니다.

#10 Telemetry / Canary / 실제 세션 로그 기반 확인

Why This Happens / 왜 이런 순서가 나오는가

쉽게 말하면, Skill 평가는 “학술 벤치마크”보다 “운영 리스크 관리”에 더 가깝기 때문입니다.

1. Skills are workflow tools

Skill은 문답 모델이 아니라 작업 흐름 도구입니다. 그래서 첫 질문은 “정답률”보다 “핵심 플로우를 끝까지 수행하는가?”가 됩니다.

2. Cheap feedback beats perfect feedback

현업은 완벽한 평가보다 빠른 경고를 원합니다. 그래서 스모크 테스트와 간단한 회귀 게이트가 먼저 자리를 잡았습니다.

3. Teams hate vague arguments

“이게 더 나은 것 같아요”는 오래 못 갑니다. 루브릭과 기준선이 인기인 이유는, 애매한 논쟁을 줄이기 때문입니다.

4. LLM judges are useful but noisy

그래서 결정적 assertion, golden output, schema check가 같이 붙습니다. 사람들은 자동 판정보다 자동 판정 + 객관 체크를 더 신뢰합니다.

5. Reliability is costly

여러 번 돌리기, 숨은 테스트, 실제 텔레메트리는 분명 중요하지만 셋업 비용이 큽니다. 그래서 상위권이 아니라 성숙도 지표처럼 보였습니다.

Plain-English Summary

가장 흔한 흐름은 이렇게 요약됩니다. “빨리 깨지는지 본다 → 실제 요청 몇 개를 돌린다 → 기준으로 점수화한다 → 이전보다 나빠졌는지 확인한다.”

Default Stack / 바로 쓸 기본 평가 묶음

Skill 하나를 실무적으로 검증한다면, 최근 흐름상 이 5단 구성이 가장 무난하고 강합니다.

추천 기본형: “거대한 평가 프레임워크”부터 만들지 말고, 아래 5단만 먼저 만들어도 공개 자료의 상위 패턴 대부분을 따라가게 됩니다.
1

Smoke Gate

핵심 기능 3개만 5분 안에 확인합니다. 실패하면 나머지 평가를 생략합니다.

2

Scenario Set

대표 요청 5~10개를 고정합니다. 정상, 엣지, 거절 케이스를 섞습니다.

3

Rubric

정확성, 완결성, 안전성, 효율, 설명성처럼 5개 항목 정도로 점수화합니다.

4

Regression Check

이전 버전 점수와 비교합니다. 특정 항목 하락 시 바로 눈에 띄게 만듭니다.

5

Reliability Re-run

변경한 핵심 시나리오만 3~5회 다시 돌려서 흔들리는지 확인합니다.

Codex vs Claude / 둘 사이의 미묘한 차이

방식 자체는 거의 수렴했지만, 강조점은 약간 달랐습니다.

Codex-leaning pattern

Codex 쪽 공개 자료는 diff review, tool trace, acceptance 전에 사람 검토를 더 강하게 드러냈습니다. 즉, “무엇을 출력했는가”뿐 아니라 “어떻게 행동했는가”를 더 많이 봅니다.

Claude-skill ecosystem pattern

Claude 쪽 스킬 마켓플레이스는 smoke-test runner, evaluation-rubrics 같은 재사용 스킬 패키징이 더 눈에 띄었습니다. 즉, 평가 자체를 또 다른 skill로 만들어 유통하는 문화가 강했습니다.

하지만 큰 흐름은 동일합니다. 두 생태계 모두 결국 빠른 게이트 + 구조화된 증거 + 회귀 방지로 수렴하고 있습니다.
